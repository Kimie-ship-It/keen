# 业务数据库备份与恢复

## 范围

本方案从 Supabase 读取八张业务表，压缩后使用 AES-256-GCM 加密，保存到项目外的 `C:\Codex使用文档工作\campus-jobs-backups\supabase`。八张表包括招聘、地点、行业、来源运行、来源状态、审核日志、登录限速和来源下架审计；招聘中的云端审核状态也包含在内。

这不是整个 Supabase 项目或 PostgreSQL 的完整备份：不包含平台账号、Auth 用户、Storage 文件、数据库角色、权限策略、自定义函数和平台设置，不提供按时间点恢复。恢复使用固定的初始迁移与来源下架追加迁移；不要改写已使用的迁移。新版 v2 包含八表；旧版 v1 七表仍可解密与隔离演练，但因缺失来源下架历史，禁止直接恢复到独立空库后公开服务，必须另行核对限制状态。

## 生成与验证

在项目目录运行：

```powershell
npm run setup:backup
npm run backup:supabase
npm run backup:supabase:verify
```

- `setup:backup` 只在没有密钥时生成，已有合法密钥会保留，不会打印密钥。
- 加密密钥保存在被 Git 忽略的 `.env.local` 的 `SUPABASE_BACKUP_KEY` 字段。必须另外安全保存；只保存加密备份而丢失密钥将无法恢复。不要发到聊天、Git、日志或网页，也不要擅自更换。
- 备份使用一致性的只读事务，分批读取；先写临时文件，解密验证通过后再改为正式文件名。
- 默认保留最近 14 份可解密有效备份，可通过 `SUPABASE_BACKUP_RETENTION_COUNT` 设置 1 至 365。损坏文件、其他密钥的备份和未完成文件不会自动删除，应人工检查。
- 验证命令默认使用文件名排序最新的一份，也可以传入指定文件。验证失败不会自动跳过并声称最新备份可用。
- 恢复演练在真实 PostgreSQL 连接中创建会话临时表，逐表比较全部内容并检查自增序号，结束后回滚，不覆盖正式表。
- 单表上限 25 万行、解压后上限 128 MiB，适合当前试点规模。超过规模会拒绝生成；扩容前需引入大规模流式备份或 PostgreSQL 专用备份方案。

## 每日运行

`collect:daily` 已接入云端业务备份。只要配置数据库连接，每次每日流程结束时都会尝试备份，所有采集来源均返回失败时也会尝试保存独立变化的云端审核数据。失败会返回非零结果并保留已有备份，飞书通知仅在机器人配置后有效。

既有 Windows 任务仍是每天 08:00、依赖本机开机和登录。2026-10-01 18:08:08 手动触发现有计划任务，自动备份和健康检查均完成，任务结果码 0；新快照 `20261001T101036628Z-60c0a06d.cjbackup` 在真实 PostgreSQL 临时表全量恢复后内容一致、自增编号正确，不覆盖正式表。详见 `docs/DAILY-TASK-ACCEPTANCE.md`。2026-10-02 08:00 的时间触发尚待观察，不能把手动触发验收当作云端定时任务已完成。

## 实际恢复到独立空库

真实生产恢复须由操作者确认，禁止覆盖正在使用的源数据库。

1. 创建独立的空 Supabase 项目，依次执行 `supabase/migrations/0001_initial_schema.sql` 和 `supabase/migrations/0002_source_controls.sql`。八张表必须存在且 RLS 开启，不能有任何业务行。
2. 在本机 `.env.local` 安全设置目标项目的 `SUPABASE_RESTORE_DB_URL`，保留原 `SUPABASE_DB_URL` 不变。目标和源数据库必须不同；同一 Supabase 项目的直连与 Pooler 地址会识别为同一个数据库并拒绝。
3. 保留原备份密钥，先验证指定备份，再执行：

```powershell
npm run backup:supabase:verify -- "C:\完整路径\备份.cjbackup"
npm run restore:supabase -- --confirm-empty-target "C:\完整路径\备份.cjbackup"
```

4. 恢复命令锁定八张目标表并检查空库、字段和 RLS，在同一事务中分批写入，逐表核对全部内容，修正自增序号；任何错误回滚。不会自动切换网站数据库。
5. 单独核验目标项目的招聘数量、隐藏状态、审核日志、来源下架历史、来源状态及网站查询，再经确认切换网站连接。切换前保留原项目和备份；切换后重启网站并重新验证访问。

独立空库恢复路径已经通过临时表集成测试；尚未新建第二个项目做真实切换验收，不应把隔离演练描述为灾难恢复全过程完成。

## 当前仍缺少的保护

- 2026-10-01 指定八表加密备份已上传百度网盘私有目录，下载副本大小及 SHA-256 与原件一致；隔离恢复复验结果见 `docs/BAIDU-OFFSITE-BACKUP.md`。密钥仍只有本机配置中的一份，电脑故障导致密钥丢失时，网盘备份也无法解密；独立密钥保存方式仍待确认，不与备份上传至同一网盘。
- GitHub 仅保存代码和文档，不保存数据库、加密备份或密钥。
- SQLite 的步骤备份和每日备份不自动包含云端管理变化；切回 SQLite 前必须另行迁移云端审核与来源下架状态，不能用旧本地状态重新公开受限招聘。回退旧代码也须先核对其是否支持来源下架。
- 单份手动上传不等于每日自动异地备份。自动上传及失败提醒、云端独立调度、平台级备份和第二个项目恢复验收仍待完成。
